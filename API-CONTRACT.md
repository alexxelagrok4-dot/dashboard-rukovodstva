# Контракт данных: что фронтенд ожидает от бэкенда

Для варианта Б (свой бэкенд + своя PostgreSQL вместо Supabase, см. `HANDOFF.md`). Здесь — исчерпывающий список всех обращений к базе, которые сейчас делает `index.html` через `supabase-js`. Задача нового бэкенда — закрыть их все эквивалентными эндпоинтами; форму (REST/GraphQL/что угодно) выбирает разработчик.

Ничего не скрыто и не сокращено — это буквально весь список запросов к БД во всём файле.

## Аутентификация

Сейчас — Supabase Auth (email+password, синтетический email `{login}@opalubka.invalid`, поле "логин" в форме — это локальная часть до `@`). Бэкенду нужно решить свою схему аутентификации, но фронтенду в любом виде нужны четыре операции:

| Операция | Сейчас (Supabase) | Что должен уметь новый бэкенд |
|---|---|---|
| Вход | `sb.auth.signInWithPassword({email, password})` | Принять логин+пароль, вернуть токен/сессию |
| Регистрация | `sb.auth.signUp({email, password})` | Создать пользователя (или убрать self-signup — решать вам; сейчас админ и ролевые логины создаются именно так, см. README «Роли и доступ») |
| Выход | `sb.auth.signOut()` | Инвалидировать сессию на клиенте |
| Проверка сессии при загрузке страницы + реакция на вход/выход | `sb.auth.onAuthStateChange(...)`, `sb.auth.getSession()` | Любой способ узнать «залогинен ли пользователь прямо сейчас» и получить его email/логин |

**Важно:** роль пользователя (admin / sales / marketing / ...) сейчас определяется на клиенте по имени логина (`LOGIN_ROLES` в коде), нигде не хранится в БД. Это сознательно упрощённый, не защищённый от обхода механизм (см. HANDOFF, раздел «Известные ограничения»). При переезде на свой бэкенд имеет смысл сразу сделать это по-нормальному — роль как поле пользователя на сервере, а не строка в JS.

## Таблицы этого дашборда

### `dash_weeks`

Столбцы: `id, week_start, created_by, created_by_email, created_at`.

- `SELECT id, week_start ORDER BY week_start DESC` — список недель для выпадающих списков.
- `INSERT (week_start, created_by, created_by_email) RETURNING *` — создание новой недели; должна быть ошибка при повторном `week_start` (уникальность).

### `dash_entries`

Столбцы: `id, week_id, metric_key, value, updated_by_email, updated_at`. Это EAV-таблица — `metric_key` может быть любой из ~54 строк, которые генерирует `buildFieldGroups()` в коде (полный список смотреть там, не хардкодить отдельно).

- `SELECT week_id, metric_key, value` **без фильтра** — да, действительно вся таблица целиком, разом, один раз при входе. Нужно для графиков динамики (спарклайны, тренды) — так и обновляется только эта переменная в памяти, без повторных запросов на каждый чарт. Если исторических данных станет много (годы), на своём бэкенде стоит это переосмыслить (пагинация/агрегация на сервере), сейчас для нескольких месяцев это не проблема.
- `SELECT metric_key, value WHERE week_id = :id` — данные одной недели (открытие недели, выбор периода сравнения).
- `UPSERT rows ON CONFLICT (week_id, metric_key) DO UPDATE` — сохранение формы, пачкой (до ~54 строк за раз).

### `dash_client_breakdown`

Столбцы, которые читает фронтенд: `client_name, amount` (плюс фильтры `week_id, product, stream`).

- `SELECT client_name, amount WHERE week_id=:id AND product=:p AND stream=:s ORDER BY amount DESC`.

**Это ключевое место для вашей автоматизации.** Сейчас в эту таблицу никто не пишет — она создана, запрос работает, но пуста (см. HANDOFF). Именно сюда должна писать выгрузка из 1С/CRM, если хотите реальную клиентскую разбивку вместо заглушки «источник не подключен».

## Таблицы другого инструмента (только чтение, кросс-интеграция)

`sb_uploads` и `sb_snapshots` **не принадлежат этому дашборду** — это таблицы инструмента «Продление-Взыскание» (СБ), дашборд их просто читает для одной-единственной плитки «Тоннаж в просрочке 29+»:

- `SELECT id, report_date FROM sb_uploads ORDER BY report_date ASC`
- `SELECT upload_id, weight_kg FROM sb_snapshots WHERE bucket = '29+'`

При переезде на свой бэкенд решите один из трёх вариантов:
1. реплицировать эти таблицы тоже (тогда СБ-инструмент тоже придётся переносить — это отдельный больший разговор);
2. временно отключить эту плитку;
3. гибрид — эта одна плитка продолжает читать из старого Supabase-проекта, а всё остальное идёт с нового бэкенда (два источника данных в одном фронтенде, технически нормально, просто два разных клиента вместо одного `sb`).

## Если пригодится: путь наименьшего сопротивления

Если цель — именно «своя PostgreSQL» (а не обязательно «полностью свой API с нуля»), можно развернуть **PostgREST** — это лёгкий open-source REST-сервер, который и есть тот слой, с которым на самом деле разговаривает `supabase-js` (Supabase = PostgREST + GoTrue-авторизация + обвязка вокруг обычного Postgres). PostgREST разворачивается отдельно, поверх любой вашей PostgreSQL, без остального Supabase. Тогда весь текущий код фронтенда (все вызовы `sb.from(...).select()...`) продолжает работать без изменений — меняется только URL и способ авторизации в `index.html`. Не обязательно, просто способ не переписывать десятки мест в коде, если это не принципиально.
