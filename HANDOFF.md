# Передача инструмента разработчику

Этот документ — для программиста, который принимает «Дашборд руководства» на дальнейшую доработку. Он не дублирует `README.md` этой папки (там — функциональное описание: показатели, SQL-схема, роли, третий уровень разбора), а объясняет то, чего README не покрывает: архитектуру кода, откуда что брать, как безопасно вносить изменения и что осталось не сделано.

Читать в таком порядке: сначала этот файл целиком, потом `README.md`, потом сам `index.html`.

> **Решено:** переезд на собственный бэкенд и собственную PostgreSQL разработчика (вариант «Б» — полная независимость от Supabase, с автоматической загрузкой данных из внутренних систем компании, а не только ручным вводом). Раздел 4 ниже и весь `API-CONTRACT.md` написаны под этот сценарий.

## 1. Что это

Еженедельный управленческий дашборд для планёрок руководства: план/факт по выручке, утилизация, себестоимость, грузооборот, маркетинговая воронка, root-cause разбор провалов. Полное описание функциональности — в `README.md`.

## 2. Архитектура — и почему она такая

Один файл `index.html`: HTML + CSS + весь JS внутри, включая бизнес-формулы. Никакого backend — единственный внешний сервис — Supabase (Postgres + Auth), доступ напрямую из браузера через `@supabase/supabase-js`.

Это осознанный выбор, общий для всех внутренних инструментов компании (тот же паттерн у СБ-инструмента «Продление-Взыскание» и калькулятора аренды):
- не нужно обслуживать отдельный сервер и деплой бэкенда;
- формулы не спрятаны — любой, кто открывает код, видит ровно то, что считает приложение (важно для доверия руководства к цифрам);
- Supabase Auth + Row Level Security закрывают вопрос многопользовательского доступа без своего authentication-слоя.

Если решите переписывать на фреймворк/бэкенд — это нормальное развитие, но тогда стоит сознательно решить, сохранять ли этот принцип прозрачности формул для нетехнических пользователей.

## 3. Где лежит код

- **Приватный репозиторий** (полная история разработки, все решения — в сообщениях коммитов): `github.com/alexxelagrok4-dot/Daya`, папка `tools/ДАШБОРД-РУКОВОДСТВА/`, ветка `agent/autonomous-box-edition`.
- **Публичное зеркало** — тот же файл, но в отдельном репозитории: `github.com/alexxelagrok4-dot/dashboard-rukovodstva`, ветка `main`. Существует только потому, что GitHub Pages нужен публичный (или платный) репозиторий для хостинга — сам инструмент от этого не менее приватен: доступ всё равно только по логину/паролю в Supabase.
- **Живой инструмент:** `https://alexxelagrok4-dot.github.io/dashboard-rukovodstva/`

До сих пор каждое изменение пушилось в оба репозитория одинаковым коммитом. Если продолжите работать так же — держите их синхронными. Если перейдёте на другой хостинг (Vercel/Netlify/свой сервер) — публичное зеркало можно упразднить и работать только в приватном репозитории.

## 4. Доступ, который понадобится (вариант «Б»: свой бэкенд)

Раз данные будут идти из вашей собственной PostgreSQL, а не из общего Supabase-проекта компании, доступ к Supabase не нужен вообще:

- **GitHub:** ничего приглашать не нужно — репозиторий с текущим кодом уже публичный, забирайте прямо сейчас: `git clone https://github.com/alexxelagrok4-dot/dashboard-rukovodstva.git`. Это тот же код, что и живой инструмент на GitHub Pages.
- **Схема БД:** полная SQL-схема (`dash_weeks`, `dash_entries`, `dash_client_breakdown`) — в `README.md`, раздел «Настройка базы». Переносите структуру таблиц как есть (или адаптируйте под свою СУБД/ORM) — это то, что сейчас реально хранит EAV-модель показателей.
- **Контракт данных:** `API-CONTRACT.md` в этой же папке — исчерпывающий список всех запросов, которые фронтенд сейчас делает к базе (auth, таблицы, точная форма каждого запроса). Это то, что новый бэкенд должен закрыть эквивалентными эндпоинтами, чтобы фронтенд продолжил работать без переделки основной логики.
- **Логин в самом приложении** (используется только в текущей, Supabase-версии, для сравнения/справки) — общий `alexxela` либо ролевые (`sales`/`marketing`/... — README «Роли и доступ»). В новой схеме аутентификации это не обязано сохраняться один в один — решать вам, но роль-модель (кто что имеет право заполнять) стоит перенести как идею.

Если позже понадобится всё же независимая копия именно на Supabase (для сравнения/отката) — тот же `README.md` содержит всё нужное; аналогичный паттерн независимой копии подробнее расписан для СБ-инструмента в `tools/ПРОДЛЕНИЕ-ВЗЫСКАНИЕ/independent-copy-setup.md`.

## 5. Модель данных: как это на самом деле устроено

Полный список всех запросов к базе, которые нужно закрыть на новом бэкенде — в `API-CONTRACT.md`. Здесь — только принципы, чтобы не сломать логику при переносе.

**EAV-таблица, не жёсткие колонки.** `dash_entries` хранит `(week_id, metric_key, value)` построчно, а не фиксированный набор колонок. Это осознанно — добавление нового показателя не требует миграции таблицы.

**Единый источник правды.** `buildFieldGroups()` в начале `<script>` генерирует из справочников (`REVENUE_STREAMS`, `PRODUCTS`, `TURNOVER_STAGES`, `CAPACITY_STAGES`, `NEW_FUNNEL_STAGES`) сразу и форму ручного ввода, и полный список метрик (`ALL_FIELDS`). **Никогда не редактируйте форму ввода и список метрик по отдельности** — расхождение между ними уже однажды было реальным багом в другом инструменте компании (см. changelog СБ-инструмента), отсюда и этот принцип.

**Ключи полей — только через функции-генераторы** (`revKey`, `turnKey`, `newFunnelKey`, `laborHoursKey` и т.д.), никогда не хардкодьте строки метрик руками. Если добавляете новый показатель — сначала добавьте элемент в соответствующий справочник (например, новую строку в `TURNOVER_STAGES`), а не отдельное поле мимо системы генерации.

**compute-функции — единственное место для формул.** `computeRevenue`, `computeUtilization`, `computeCapacity`, `computeCostForProduct`, `computeRepairShare`, `computeNewFunnel`, `computeMarketing`, `computeMonthlyProgress` и т.д. Каждая принимает необязательный второй параметр `get` (функция чтения значения по ключу) — по умолчанию `num` (текущая открытая неделя), но можно передать `numWas` (неделя сравнения) или `getterForWeek(anyWeekId)` (любая произвольная неделя). Именно так графики динамики, спарклайны, «На что смотреть» и «Месячная динамика» переиспользуют одни и те же формулы, что и плитки — ни одна цифра не считается дважды разными путями.

**Три уровня экрана:**
- **level1** — сетка плиток (`renderTiles`);
- **level2** — разбор по конкретной плитке (`renderDrilldown`, ключ — `openTileKey`);
- **level3** — воронка/клиенты по конкретному потоку выручки (`renderLevel3`, состояние — `openStreamProduct`/`openStreamKey`/`level3Tab`).

Переходы между уровнями — через `showLevel1()`/`showLevel2(key)`/`showLevel3(product, streamKey, tab)`, а не прямые манипуляции DOM — если добавляете новый экран, следуйте этому же паттерну (иначе легко сломать кнопку «назад», такой баг уже был и был исправлен).

## 6. Как тестировать логику перед тем, как пушить

В процессе разработки для каждой новой формулы использовался один и тот же приём — не поленитесь повторять его, он не раз ловил реальные баги до продакшена:

1. Извлечь `<script>` из `index.html` регулярным выражением в отдельный `.js`-файл.
2. Подставить в конец, перед закрывающим `})();`, что-то вроде `globalThis.__ex = { computeCapacity, computeRepairShare, ... };`.
3. Застабить `document.getElementById` (фейковый элемент с `style`, `addEventListener`, `querySelectorAll`) и `window.supabase.createClient` (пустая цепочка `.from().select()...`), чтобы верхнеуровневый код не падал без реального DOM/сети.
4. `require()` получившийся файл из Node-скрипта, вызвать нужные функции с руками собранными тестовыми данными, сверить с посчитанным вручную ожидаемым результатом.

Это не формальный test suite (его нет), а разовая проверка перед каждым пушем — но именно она поймала реальные ошибки (перепутанный знак в сортировке, неверная историческая база в расчёте риска, и другие) до того, как это увидело руководство.

## 7. Известные ограничения и что дальше

Не забытое, а сознательно отложенное — с указанием, почему:

- **`dash_client_breakdown` — таблица есть, писателя нет.** Провал в поток выручки → вкладка «Клиенты» всегда пустая: таблица создана и запрос к ней работает, но данные туда никто не пишет — ручной еженедельный ввод списка клиентов посчитали неоправданной нагрузкой. Ждёт автоматической выгрузки из 1С. Когда источник появится — нужен только загрузчик (insert в `dash_client_breakdown`), сам UI менять не придётся.
- **RBAC — только на стороне браузера.** Ролевые логины (`sales`, `marketing`, ...) не могут редактировать чужие поля в форме, но это проверка в JS, не RLS-политика в Postgres — теоретически можно обойти прямым вызовом API с теми же кредами. Для доверенной внутренней команды посчитали это достаточным; если понадобится настоящая изоляция — нужна таблица ролей и RLS-политика на `dash_entries`, привязанная к `auth.uid()`.
- **Retention-воронка для «Повторных сделок» / «Продлений» не построена.** У них другая причинная модель (не маркетинг, а удержание: активная база → договоры к продлению → контакт менеджера), сознательно не стали копировать логику воронки «Новых» — решение было явно проговорено с заказчиком.
- **Источник лидов (вероятно Bitrix24) не подключен** — воронка «Новые клиенты» пока вводится вручную.
- **Маржа/P&L сознательно не в дашборде.** Обсуждалось отдельно: затраты, важные для реальной прибыльности (аренда, амортизация, SG&A), по природе месячные, а выручка в этом инструменте — кассовая за неделю; смешивать их в одну недельную цифру значило бы получить точную на вид, но неверную по сути метрику. Себестоимость операции (уже в дашборде) — корректный недельный прокси эффективности.
- **Капасити:** нет разделения «не хватило рук» (мало часов) от «отработали неэффективно» (низкая факт. выработка при тех же часах) — обсуждалось, не реализовано, потребовало бы отдельного поля «плановые человеко-часы».

## 8. Деплой

GitHub Pages из публичного зеркала, ветка `main`, корень репозитория. После пуша Pages пересобирается не мгновенно — проверяйте не через `gh api .../pages/builds/latest` (наблюдалась задержка отчёта о статусе), а прямым запросом содержимого страницы (`curl` по URL с параметром типа `?v=timestamp`, чтобы обойти кэш, и поиском строки, которая точно появилась в новом коде).
