# ДАШБОРД-РУКОВОДСТВА

Еженедельный управленческий дашборд для планёрок с руководителями: план/факт по выручке, утилизации, стоимости аренды, грузообороту, человеко-часам и себестоимости операции — раздельно опалубка (тонны) и бытовки (штуки).

Структура и логика показателей зафиксированы в артефакте-черновике (дерево показателей, схема воронки лид→сделка, открытые решения) — см. историю обсуждения. Ключевой принцип: «Выручка» — это физическое поступление денег за неделю (касса, не начисление), и раскладывается не на «причины», а на **сумму четырёх независимо планируемых денежных потоков**, у каждого своя ответственная служба:

| Поток | Служба |
|---|---|
| Новые клиенты | Продажи |
| Повторные сделки | Продажи (клиентский менеджер) |
| Продления договоров | Продажи (клиентский менеджер) |
| Собрано по долгу | Безопасность |

Файл `index.html` — самодостаточный (как и остальные инструменты компании), использует тот же Supabase-проект и тот же общий логин/пароль, что и «ПРОДЛЕНИЕ-ВЗЫСКАНИЕ» — отдельного аккаунта заводить не нужно.

## v1: ручной ввод

Автоматических выгрузок пока нет ни по одному потоку (кроме того, что уже есть в DAYA) — первая версия работает на **еженедельном ручном вводе** 32 показателей через форму. Источники по каждому потоку подключаются по мере готовности, один за другим — так же поэтапно, как развивался инструмент СБ (см. его changelog).

Известные источники на будущее:
- **Опалубка** — данные по сделкам/договорам/движениям уже есть в DAYA.
- **Бытовки** — учёт ведётся в 1С (формат выгрузки уточняется).
- **Лиды / целевые лиды** — источник будет определён позже (вероятно Bitrix24).

## Настройка базы (один раз)

Используется тот же Supabase-проект, что и у инструмента «ПРОДЛЕНИЕ-ВЗЫСКАНИЕ» — просто добавляются две новые таблицы. В **SQL Editor** этого проекта выполнить:

```sql
create extension if not exists pgcrypto;

create table public.dash_weeks (
  id uuid primary key default gen_random_uuid(),
  week_start date not null unique,
  created_by uuid references auth.users(id),
  created_by_email text,
  created_at timestamptz not null default now()
);

create table public.dash_entries (
  id uuid primary key default gen_random_uuid(),
  week_id uuid references public.dash_weeks(id) on delete cascade,
  metric_key text not null,
  value numeric,
  updated_by_email text,
  updated_at timestamptz not null default now(),
  unique(week_id, metric_key)
);
create index dash_entries_week_id_idx on public.dash_entries(week_id);

-- Клиентская разбивка потоков выручки (см. "Третий уровень" ниже) — таблица уже
-- готова принимать данные, но пока её никто не заполняет: ручной ввод списка клиентов
-- каждую неделю — заметная лишняя нагрузка, поэтому ждём автоматическую выгрузку из 1С.
create table public.dash_client_breakdown (
  id uuid primary key default gen_random_uuid(),
  week_id uuid references public.dash_weeks(id) on delete cascade,
  product text not null,
  stream text not null,
  client_name text not null,
  amount numeric not null,
  source text,
  created_at timestamptz not null default now()
);
create index dash_client_breakdown_lookup_idx on public.dash_client_breakdown(week_id, product, stream);

alter table public.dash_weeks enable row level security;
alter table public.dash_entries enable row level security;
alter table public.dash_client_breakdown enable row level security;

create policy "read for authenticated" on public.dash_weeks for select using (auth.role() = 'authenticated');
create policy "insert for authenticated" on public.dash_weeks for insert with check (auth.role() = 'authenticated');

create policy "read for authenticated" on public.dash_entries for select using (auth.role() = 'authenticated');
create policy "insert for authenticated" on public.dash_entries for insert with check (auth.role() = 'authenticated');
create policy "update for authenticated" on public.dash_entries for update using (auth.role() = 'authenticated');

create policy "read for authenticated" on public.dash_client_breakdown for select using (auth.role() = 'authenticated');
create policy "insert for authenticated" on public.dash_client_breakdown for insert with check (auth.role() = 'authenticated');
create policy "update for authenticated" on public.dash_client_breakdown for update using (auth.role() = 'authenticated');
create policy "delete for authenticated" on public.dash_client_breakdown for delete using (auth.role() = 'authenticated');

-- Без этих GRANT политики RLS выше не сработают — в Supabase создание таблицы через
-- SQL Editor не выдаёт права роли authenticated автоматически (в отличие от Table
-- Editor). Без этого блока запросы падают с "permission denied", даже когда RLS
-- настроена верно.
grant select, insert, update, delete on public.dash_weeks to authenticated;
grant select, insert, update, delete on public.dash_entries to authenticated;
grant select, insert, update, delete on public.dash_client_breakdown to authenticated;
```

Значения хранятся построчно (метрика → число за неделю), а не жёсткими колонками — так проще добавлять новые показатели позже, не меняя структуру таблицы и не требуя миграций.

## Роли и доступ

Один общий Supabase-проект, но у каждой службы может быть свой логин — тогда форма ввода показывает все поля (для контекста), но редактировать можно только поля своей службы, остальные — серые и заблокированы. Логин `alexxela` (и любой не из списка ниже) — администратор, видит и правит всё, как раньше.

Завести логин службы — обычная регистрация через экран входа («Зарегистрироваться»), логином должно быть одно из зарезервированных имён:

| Логин | Служба |
|---|---|
| `sales` | Продажи |
| `marketing` | Маркетинг |
| `logistics` | Логистика/Склад |
| `repair` | Ремонт |
| `security` | Безопасность |
| `commercial` | Коммерческий директор |

Это проверка на стороне браузера (как `ADMIN_LOGINS` в СБ-инструменте), а не изоляция на уровне базы — общий логин технически всё ещё может править любое поле напрямую через API. Для этого инструмента (доверенная внутренняя команда) этого достаточно; настоящая защита на уровне RLS — отдельная задача, если понадобится.

## Список показателей (54 поля ввода)

Генерируются в коде из справочников — единый источник для формы ввода и для плиток, расхождение между ними исключено конструктивно:

- `REVENUE_STREAMS` × `PRODUCTS` — выручка, 16 полей (план/факт × 4 потока × 2 продукта).
- `NEW_FUNNEL_STAGES` × `PRODUCTS` + затраты на маркетинг — воронка «Новые клиенты» (квалифицированные лиды → КП → заказ), 8 полей. Начинается сразу с **квалифицированных** лидов, а не с сырых обращений — маркетинг уже отсеял мусор, и только это число имеет управленческий смысл. Только для потока «Новые» — у «Повторных»/«Продлений» другая причинная модель (retention, не маркетинг), у «Собрано по долгу» — уже есть отдельный root-cause инструмент (СБ «Продление-Взыскание»).
- `PRODUCTS` — утилизация, 4 поля.
- `PRODUCTS` × `TURNOVER_STAGES` + сейчас у клиента + остаток в ремонте + общий парк — грузооборот и расположение парка, 14 полей.
- `PRODUCTS` × `CAPACITY_STAGES` (приёмка/отгрузка, ремонт) — человеко-часы, ФОТ и норма т(шт)/чел-час, 12 полей. Часы и ФОТ введены **отдельно по продуктам**, хотя бригада одна и та же на оба продукта — потому что нормы т/чел-час и шт/чел-час несовместимы, и без разделения «% загрузки мощностей» посчитать нельзя.

Маркетинг — отдельная выделенная плитка на первом экране (не спрятана внутри разбора выручки): квалифицированные лиды и стоимость одного лида (затраты / лиды). Клик ведёт в ту же воронку, что и «Новые клиенты» в выручке.

«Себестоимость операции» и «% загрузки мощностей» не вводятся вручную — вычисляются:

```text
план мощности (100%) = человеко-часы × норма
% загрузки = факт / план мощности × 100
себестоимость, ₽/ед = ФОТ / обработанный объём
```

## Доля парка в ремонте

Отдельная метрика в разбивке грузооборота — остаток «сейчас в ремонте» к общему парку (не путать с «поступило в ремонт за неделю», это поток). Порог: план — не более 3%; 3–5% — «выше нормы»; больше 5% — «критично выше нормы».

## Третий уровень: где именно оборвалось

По клику на «Новые клиенты» в разборе выручки открывается экран с двумя вкладками:

- **Воронка** — квалифицированный лид → КП → заказ, с конверсией между этапами и привязкой каждого этапа к службе (лиды — маркетинг; КП/заказы — продажи). Автоматический «диагноз недели» сравнивает воронку с предыдущей сохранённой неделей (не с выбранным периодом сравнения — работает всегда) и называет этап с наибольшим падением конверсии и его службу, либо, если конверсии не просели, а упал приток лидов — указывает на маркетинг напрямую.
- **Клиенты** — таблица «клиент → сумма» по этому потоку за неделю. Пока всегда пустая (см. `dash_client_breakdown` выше) — функциональность готова, источник (1С) не подключен, ручной ввод намеренно не делаем.

«Повторные сделки» и «Продления» открывают только вкладку «Клиенты» — у них нет маркетинговой воронки (другая причинная модель, retention: активная база, договоры к продлению, контакт клиентского менеджера), но декомпозиция по клиентам всё равно осмысленна.

Разбор утилизации теперь в две колонки: слева — расшифровка, где сейчас физически находится парк (% у клиента / % в ремонте / % на складе — остаток на складе не вводится, а считается: общий парк минус два других числа), плюс разбивка недобора относительно плана (простой в ремонте / дефицит спроса — с той же кликабельной ссылкой в воронку «Новые», так как причина часто одна и та же); справа — график динамики утилизации по неделям.

Разбор себестоимости и «Загрузки мощностей» — перекрёстная ссылка друг на друга без дублирования данных: это одна и та же арифметика (ФОТ / объём), просто с разных сторон.

«Собрано по долгу» не дублируется здесь — там уже есть полноценный root-cause инструмент (СБ «Продление-Взыскание», разбор по контрагентам), ссылка на него — прямо в разборе выручки.

**Графики факт/план** (выручка) — столбцовые, не линейные: план и факт за неделю — это не точки на непрерывной кривой, между которыми существует «промежуточное» значение, а два самостоятельных числа за период, поэтому парные столбцы читаются честнее. Остальные графики (проценты, тренды, счётчики) — линейные, там непрерывность имеет смысл.

## Динамика между периодами

В карточке «Неделя» есть «Сравнить с периодом» — при выборе все плитки показывают дельту факта к выбранной неделе («было → стало»), не только план/факт текущей недели. Сравнение всегда пересчитывается той же формулой, что и «сейчас» — просто с других значений (see `computeRevenue(product, get)` и аналоги в коде — второй параметр `get` переключает источник между текущей и сравниваемой неделей).
